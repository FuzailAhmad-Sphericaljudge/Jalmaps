# Internationalisation (i18n)

JalMaps ships **English (`en`) and Hindi (`hi`)**. Every route is locale-prefixed
(`/en/…`, `/hi/…`), every user-facing string lives in a message file, and two CI
gates keep the locales consistent. This document explains the architecture and
the "how to add a locale" recipe.

## Architecture

```
src/i18n/
  config.ts            locales, defaultLocale, format locales, native names
  routing.ts           next-intl routing contract (localePrefix: "always")
  navigation.ts        locale-aware Link / redirect / useRouter / usePathname
  request.ts           per-request messages + pseudo-localisation + timezone
  types.d.ts           AppConfig augmentation → typed t("…") keys
  fonts.ts             per-locale font stack (en: Inter; hi: Inter + Noto Sans Devanagari)
  icu.ts               minimal ICU parser (arguments, plural/select options)
  pseudo.ts            pseudo-localisation transform (dev-time layout testing)
  messages/
    registry.ts        per-locale dynamic import loaders + EnglishMessages type
    en/*.json          5 namespaces: common, home, gallery, settings, errors
    hi/*.json          same 5 namespaces, same keys (enforced)
src/proxy.ts           Next 16 proxy (renamed middleware): locale negotiation,
                       NEXT_LOCALE cookie persistence, ?pseudo=1/0 cookie toggle
```

### Routing

`routing.ts` sets `localePrefix: "always"`: `/` redirects to the negotiated
locale (saved `NEXT_LOCALE` cookie → `Accept-Language` header → default `en`).
The proxy in `src/proxy.ts` wraps `next-intl/middleware` and additionally
handles the pseudo-localisation toggle: visiting any page with `?pseudo=1` sets
a `jalmaps-pseudo` session cookie; `?pseudo=0` clears it.

Routes live under `src/app/[locale]/`, with `generateStaticParams` returning
every locale, so both `/en` and `/hi` prerender at build time. The layout sets
`<html lang={locale}>` and the per-locale font class.

### Messages and typing

The registry (`messages/registry.ts`) maps each locale to async imports of its
namespace files. The `satisfies` clause (never a return-type annotation) keeps
JSON inference intact; `EnglishMessages` flows into the `AppConfig`
augmentation in `types.d.ts` (which must augment **`use-intl`**, not
`next-intl`), so `t("…")` calls are compile-checked against the English key
tree. Adding a key to any `en/*.json` immediately extends the allowed keys;
`hi` parity is enforced by the CI gate below.

### Formatters

`src/lib/format/numbers.ts` and `depth.ts` format numbers/dates via
`localeToFormatLocale` (`en-IN` / `hi-IN`) in `Asia/Kolkata`. Note: `hi-IN`
renders **Latin digits by default** (Devanagari digits would need an explicit
`u-nu-deva` locale extension) — this is deliberate and asserted in tests.

### Guards

- **`pnpm check-i18n`** (`scripts/check-i18n.ts`): compares every locale
  against English per namespace — missing/extra keys, ICU argument mismatch,
  plural/select option drift. Runs as part of `pnpm check`.
- **ESLint `jalmaps/no-raw-jsx-text`** (`eslint-rules/no-raw-jsx-text.mjs`):
  errors on literal JSX text in `src/**` (tests excluded). Whitespace, the
  JalMaps wordmark, `code`/`pre`/`option` content, and explicit expression
  containers (`{"⌂"}`) are allowed. Use `t("key")` for all copy.
- **Pseudo-localisation**: enable with `NEXT_PUBLIC_PSEUDO_LOCALE=1` or
  `?pseudo=1`. English copy is transformed with accents, combining
  diaereses and `[…!!!]` brackets (~40% expansion), exposing clipped layouts
  and any string the rule above missed.

## How to add a locale (e.g. Tamil `ta`)

1. **`src/i18n/config.ts`** — add `"ta"` to `locales`, a native name to
   `localeNativeNames` (`தமிழ்` — never translated), and a format locale to
   `localeToFormatLocale` (`ta-IN`).
2. **`src/i18n/messages/ta/`** — create `common.json`, `home.json`,
   `gallery.json`, `settings.json`, `errors.json` translated from `en/`.
3. **`src/i18n/messages/registry.ts`** — add a `ta` loader mirroring `hi`.
4. **Fonts** — if the language needs a new script, extend `src/i18n/fonts.ts`
   (`getFontClassName`) and the `html[lang=…]` CSS stack in `globals.css`.
   Latin-script languages need nothing.
5. **Verify** — `pnpm check-i18n` must pass; `pnpm build` prerenders the new
   prefix; the e2e i18n spec patterns in `e2e/i18n.spec.ts` can be extended.

No other file changes: routing, negotiation, switching, typing and checks all
derive from `config.ts`.

## Adding or changing a string

1. Add/patch the key in **both** `src/i18n/messages/en/<ns>.json` and
   `hi/<ns>.json` (same key tree, same ICU arguments and plural options).
2. Use it via `t("<ns>.<key>")` (client) or
   `await getTranslations("<ns>")` (server). Keep ICU plurals with explicit
   `=0`/`one`/`other` branches.
3. `pnpm check-i18n` confirms parity; the ESLint rule prevents re-introducing
   raw copy.

## Testing

- Unit: `src/i18n/*.test.ts` (config, fonts, ICU parser, pseudo), formatters,
  LanguageSwitcher, ESLint rule (`src/lint/`), checker fixtures
  (`scripts/check-i18n.test.ts`).
- E2E: `e2e/i18n.spec.ts` — redirect, fallback, switching (home + nested),
  `NEXT_LOCALE` persistence, pseudo brackets + overflow smoke.
- Vitest notes: `next-intl`/`use-intl` are inlined (`vitest.config.mts`) and
  `next/font/google` + `next/navigation` are mocked in `vitest.setup.mts`;
  components calling `useTranslations` need a `NextIntlClientProvider` wrapper
  or an explicit label prop in tests.
